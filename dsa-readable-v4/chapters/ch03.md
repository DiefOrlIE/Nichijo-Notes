我们在上一章研究线性表时，习惯允许在任意合法位置插入或删除。但有很多问题偏偏不需要这份自由：临时放进去的东西，往往应当先取出来；旧的工作要先等待，等最新的工作结束后才能继续。程序中的函数调用、编辑器的撤销操作、尚未配对的左括号，都带有这种共同的顺序特征。本章从这个顺序出发，逐步得到一个足够简单、却用途极广的数据结构：栈。

## 03.1 栈的定义与 LIFO {#v4-stack-model}

<p class="section-epigraph">当我们只能动最上面一个元素</p>
先想象桌上叠着三本书。最先放上去的是《算法》，随后是《离散数学》，最后是《数据结构》。如果三本书不能从中间直接抽走，那么接下来最方便拿到的是《数据结构》，拿走它以后才轮得到《离散数学》。这件事对每一本书都成立：**最后放进去的，最先能够取出来**。

把书替换为任意数据项，我们便得到了栈（Stack）。栈也是线性结构，元素依然有先后次序，但它对操作位置施加严格限制：只能从同一端加入、取出和查看元素。这个操作端称为**栈顶**；另一端称为栈底。这条限制通常称为后进先出（LIFO，Last In, First Out）。

“后进先出”容易使人误以为栈会自动把全部元素倒序。其实只有在**全部入栈后再依次出栈**时，出栈次序才恰好是入栈次序的逆序。只要进出交替发生，情况就更丰富。例如执行：

| 操作 | 操作结束后栈内状态（左边为栈底，右边为栈顶） | 本次返回值 |
|---|---|---|
| 初始 | [] | — |
| push(3) | [3] | — |
| push(8) | [3,8] | — |
| pop() | [3] | 8 |
| push(5) | [3,5] | — |
| top() | [3,5] | 5，栈不改变 |
| pop() | [3] | 5 |

这里的 <code>push(x)</code> 是把 x 压到栈顶，<code>pop()</code> 是移除栈顶元素，<code>top()</code> 只查看栈顶。你可以从表中发现，<code>pop</code> 和 <code>top</code> 有一个关键区别：后者不改变栈，所以连续调用两次 <code>top</code> 会读到同一个值。空栈时若还要求 pop/top，就必须明确采用哪种错误处理方式；课堂中的裸数组版本可能先判断并返回失败，标准库的某些接口则要求调用者先确保非空。

为什么需要规定得这么严格？因为如果一个结构允许随意读取和删除中间元素，我们就无法依靠“栈顶就是最近待处理的一项”这个性质推导后面的算法。栈的强大之处，正来自它把操作顺序变成了一个可以依赖的约束。

## 03.2 顺序栈与 top 指针 {#v4-stack-array}

<p class="section-epigraph">把规则落实到数组：top 究竟表示什么</p>
我们已经知道栈在逻辑上应如何表现，现在才考虑怎样存储它。最简单的做法是准备一个数组，把最早入栈的数据放在低下标，后来的数据依次放在右边。例如 [3,8,5] 存于数组下标 0、1、2，最后一个有效数据就是栈顶。

如果只记录数组和容量，还无法直接知道下一个值应放在哪里。因此增加整数 <code>top</code>，约定它表示**最后一个有效元素的下标**。请特别注意，“top 的意义”是由实现者约定的，并非语言天然规定的。

在这个约定下，空栈没有有效元素，故 <code>top=-1</code>；容量 m 的数组最后合法下标是 m−1，故 <code>top==m−1</code> 时满。压栈时要先确定还有空间，然后把 top 加一，再写入数据；弹栈时先确定非空，读出 top 对应的元素，再让 top 减一。

假设容量为 4，执行四次 push，再 pop 一次。下面特别记录容易弄混的**数组槽位**与**有效栈范围**：

| 操作 | top | 有效的数组范围 | 说明 |
|---|---:|---|---|
| 初始化 | −1 | 空 | 数组虽分配了 4 格，尚无有效栈元素 |
| push(10) | 0 | a[0]=10 | 下一项要放在下标 1 |
| push(20) | 1 | a[0..1] | 栈顶是 20 |
| push(30) | 2 | a[0..2] | 栈顶是 30 |
| push(40) | 3 | a[0..3] | 栈满；再 push 必须拒绝 |
| pop() | 2 | a[0..2] | 返回 40；原 a[3] 的旧值即使仍在内存，也不属于栈 |

请注意最后一行：<code>pop</code> 通常无需把已弹位置清零。栈的有效性由 top 决定。把 a[3] 的旧值再打印出来，只是在查看已经不属于逻辑栈的存储槽位。

完整实现可以写得相当简洁：

~~~cpp
#include <stdexcept>
#include <vector>

class IntStack {
    std::vector<int> data;
    int topIndex = -1;  // 最后一个有效元素的下标

public:
    explicit IntStack(int capacity) {
        if (capacity <= 0)
            throw std::invalid_argument("capacity must be positive");
        data.resize(capacity);
    }

    bool empty() const { return topIndex == -1; }
    bool full()  const { return topIndex + 1 == (int)data.size(); }

    bool push(int x) {
        if (full()) return false;
        data[++topIndex] = x;
        return true;
    }

    bool pop(int& x) {
        if (empty()) return false;
        x = data[topIndex--];
        return true;
    }

    int top() const {
        if (empty()) throw std::underflow_error("empty stack");
        return data[topIndex];
    }
};
~~~

阅读代码时，可以把每个条件重新翻译成一句汉语。<code>full()</code> 问的是“再往右移动一个位置是否会超出容量”；<code>empty()</code> 问的是“当前有没有任何合法下标”。这样的翻译比背 <code>++top</code> 或 <code>top--</code> 的位置更可靠。

另一类实现把 top 定义为**下一空位置的下标**，空栈时 top=0，压栈写 <code>data[top++]</code>，弹栈读 <code>data[--top]</code>，满条件 top=m。两种方法都正确，但不能把第一种的初值与第二种的操作式拼在一起。如果题目给了一份代码，先通过初值和第一次 push 判断 top 的意义，再填其他条件。

链栈也遵循相同规则。若链表头指向栈顶，push 就是头插结点，pop 就是删除首结点，均只改少量指针，时间 O(1)。数组版的优点是存储连续、无需每次为结点分配内存；链版的空间随元素数变化，但每个结点还要保存一条 next 链接。这样，逻辑上的同一种栈便有了不同的物理实现。

## 03.3 括号匹配 {#v4-brackets}

<p class="section-epigraph">括号匹配：栈保存了什么信息</p>
现在研究第一个真正需要栈的算法。给定字符串 <code>{[()]}</code>，程序要判断其中的括号是否正确配对。乍看可以分别数左括号和右括号的个数：两边数量相等就成功。但 <code>(]</code> 中左、右括号也各一个，类型却不一致；<code>)(</code> 的数量也相等，关闭括号甚至出现在对应打开括号之前。

更深的困难在于**嵌套**。读到 <code>{[(</code> 时，我们知道三个括号都尚未关闭；下一个右括号只能关闭最近打开的 <code>(</code>，不能越过它先去关闭 <code>[</code>。因此需要记住一组“已打开、还没关闭”的括号，而且每次先取最近打开的一个——这正是栈。

手工走一遍 <code>{[()]}</code>：

| 读到的字符 | 采取的动作 | 动作后栈（底→顶） | 依据 |
|---|---|---|---|
| { | push({) | [{] | 尚未找到对应的 } |
| [ | push([) | [{,[] | 还没有遇到 ] |
| ( | push(() | [{,[,(] | 最近打开的是 ( |
| ) | pop 并检查 ( | [{,[] | 与当前栈顶 ( 相匹配 |
| ] | pop 并检查 [ | [{] | 与当前栈顶 [ 相匹配 |
| } | pop 并检查 { | [] | 全部括号已关闭 |

从表里可以抽象出规则。遇左括号就入栈；遇右括号时如果栈空，立刻失败，因为没有可以配对的左括号；如果栈非空，弹出栈顶并检查类型是否匹配，若不匹配则失败。扫描结束还要检查栈是否为空，否则意味着存在尚未关闭的左括号。

这里的**正确性理由**很重要：任意一个右括号必须关闭此前尚未关闭、且离它最近的左括号。我们通过栈顶准确保存这个对象，因此可以在读到右括号的一瞬间决定是否合法。无需在输入中向前回溯。

这个方法也适用于带类型的嵌套标签等问题，但如果题目要求忽略字符串字面量中的括号，或者处理转义字符，就需要在“读入字符”阶段先识别哪些括号具有语法作用。栈负责匹配顺序，输入语义仍由题目决定。

## 03.4 后缀表达式求值 {#v4-postfix}

<p class="section-epigraph">表达式计算中，哪些工作必须暂时等待</p>
括号匹配揭示了栈的一般用途：它可以保存**暂时还不能完成的工作**。表达式计算里同样存在等待。比如 <code>3+4*5</code>，从左向右读到 <code>3+</code> 时不能马上计算加法，因为右操作数可能是整个 <code>4*5</code>。如果把 <code>+</code> 暂时存起来，等更高优先级的运算完成后再处理，就不会算错。

为了研究得更清楚，先认识两种表达式表示法。常见的 <code>A+B*C</code> 把运算符写在两个操作数之间，叫**中缀表达式**；<code>A B C * +</code> 把运算符放在它作用的操作数之后，叫**后缀表达式**（也称逆波兰式）。后缀表达式的一个好处是：只需从左到右读，不必在计算时反复考虑优先级和括号。

我们直接计算一个数值例子。后缀式 <code>8 2 / 3 4 * + 5 -</code> 的栈状态如下：

| 扫描项 | 动作后运算数栈（底→顶） | 说明 |
|---|---|---|
| 8 | [8] | 操作数直接入栈 |
| 2 | [8,2] | 继续保存 |
| / | [4] | 先弹右数 2，再弹左数 8，计算 8/2 |
| 3 | [4,3] | — |
| 4 | [4,3,4] | — |
| * | [4,12] | 3×4=12 |
| + | [16] | 4+12=16 |
| 5 | [16,5] | — |
| - | [11] | 16−5=11 |

为什么对减法、除法要特别强调弹出顺序？假设栈顶是 2，下面是 8，表达式想表示 <code>8/2</code>。若先弹出的 2 当成左操作数，得到 <code>2/8</code>，答案立即错了。应先把弹出的第一个值记为右操作数 b，第二个值记为左操作数 a，再执行 <code>a op b</code>。

栈里每次存的可以是整数、浮点数，或者已经计算出的子表达式结果。只要每个二元运算符都能从栈顶取出两个操作数，整个表达式就能逐步收缩成最终一个结果。算完以后如果栈为空或仍剩多个值，应按表达式输入不合法处理。

## 03.5 中缀转后缀 {#v4-conversion}

<p class="section-epigraph">中缀转后缀：真正需要决定的是“何时输出运算符”</p>
我们已经会算后缀式，但人输入的通常是中缀式。所以再解决一个问题：怎样把 <code>A+B*C-D</code> 改成可以直接计算的后缀顺序？

操作数 A、B、C、D 的相对次序保持不变，难点全部集中在运算符的输出时间。读到 <code>+</code> 时，我们知道 A 已经读过，却不知道加法右边是否包含乘法；因此先把 + 压入一个**运算符栈**。读到 <code>*</code> 时，由于乘法的优先级高于栈顶的 +，应当让 * 先完成，所以将 * 压在 + 上面。读到 <code>-</code> 时，需要先完成尚未输出的 * 和 +，于是依次把它们弹出输出，然后压入 -。

下面列出每一轮完整状态，避免读者必须靠猜测知道运算符何时离开栈：

| 读到 | 后缀输出区 | 运算符栈（底→顶） | 为什么 |
|---|---|---|---|
| A | A | [] | 操作数直接输出 |
| + | A | [+] | 等待右操作数 |
| B | A B | [+] | 操作数直接输出 |
| * | A B | [+,*] | * 优先级高于 +，先保存 |
| C | A B C | [+,*] | — |
| - | A B C * + | [-] | * 与 + 均应先于新来的 - 完成 |
| D | A B C * + D | [-] | — |
| 输入结束 | A B C * + D - | [] | 将剩余运算符依次弹出 |

因此转换规则可以从这个例子推出来：遇操作数直接输出；遇运算符，就把栈顶那些**应当先完成**的运算符弹出，随后压入当前运算符。对左结合运算符而言，栈顶优先级等于当前运算符时也应先弹出，因为 <code>A-B-C</code> 按通常约定是 <code>(A-B)-C</code>。但如果运算符右结合，例如常见数学约定中的幂运算 <code>2^3^2=2^(3^2)</code>，遇到同优先级的 ^ 就不能照左结合规则弹出。

括号怎样处理？左括号告诉我们括号内的运算应当先于括号外完成，因此将 <code>(</code> 作为分界标记压入运算符栈；遇 <code>)</code> 时一直弹出并输出运算符，直到读到对应的 <code>(</code>，两侧括号均不输出。比如 <code>(A+B)*C</code> 会先输出 <code>A B +</code>，再输出 C 和 *，得到 <code>A B + C *</code>。

还有一个往往被简单教程忽略的问题：**一元运算**。在 <code>-A+B</code> 中，第一个 - 没有左操作数，属于一元取负；在 <code>A-B</code> 中则是二元减法。若把它们都当二元减号，后缀计算会试图为第一个 - 弹出两个数，造成错误。可以在词法分析时把一元负号记为单独运算符 <code>NEG</code>，其计算只弹一个操作数。类似地，C++ 中的 <code>!</code> 是一元逻辑非，而 <code>&&</code>、<code>||</code> 为二元逻辑运算符。转换题必须服从题目给出的运算符优先级、结合性和元数约定。

为了真正读懂程序，你可以把“转换”想成两条互不混淆的轨道：一条是输出区，读到操作数就沿这条轨道向右追加；另一条是运算符栈，等待时压栈、确定应先执行时弹出追加到输出。遇到表达式转换题，把这两列状态一行一行写清楚，自然就不会把栈顶和后缀输出混为一谈。

## 03.6 栈与列车调度 {#v4-trains}

<p class="section-epigraph">列车调度：栈能生成哪些次序</p>
到这里我们见过两种用途：栈保存未配对的左括号，也保存尚未输出的运算符。下面换一个看上去完全不同的应用：铁路旁线。假设五节车厢编号 1、2、3、4、5，只能按这个顺序从入口进入一条单端旁线；旁线允许从同一端进出，因而是一个栈。我们希望车厢离开时遵守指定的目标顺序。

给出目标 <code>3,2,5,4,1</code>，问是否存在合法的入栈/出栈安排。为了先让 3 出站，1 和 2 必须先进入旁线，然后让 3 入栈并立即弹出；此时旁线还有 1、2，目标下一个就是 2，直接弹出即可。接下来要求 5，必须按顺序再让 4、5 进入，再依次弹出 5、4，最后弹出 1。

| 动作 | 当前栈（底→顶） | 已输出序列 |
|---|---|---|
| I1,I2,I3 | [1,2,3] | [] |
| O3 | [1,2] | [3] |
| O2 | [1] | [3,2] |
| I4,I5 | [1,4,5] | [3,2] |
| O5,O4 | [1] | [3,2,5,4] |
| O1 | [] | [3,2,5,4,1] |

完整事件轨迹写成 <code>I1 I2 I3 O3 O2 I4 I5 O5 O4 O1</code>。这里 I 表示“下一个未入栈的车厢入栈”，O 表示“当前栈顶出栈”；I 与 O 不是车厢编号，也不能随意选未来的车厢先入栈。

怎样判断一个目标序列**不可能**实现？设目标是 <code>3,1,2,4,5</code>。为了先输出 3，仍要压入 1、2、3；弹出 3 后，栈顶是 2，目标却要求 1。我们无法越过 2 直接取出 1，也不能把 2 移到别处再取 1，因此立刻判定不可能。注意这是一个具体、可验证的阻碍：**目标元素已经在栈里，却被别的元素压住**。

可以把判断过程写成贪心模拟：依次考虑目标 nextWanted；如果栈顶已经是它，就弹出；否则不断把尚未进入的车厢按原顺序压栈，直到顶端成为 nextWanted 或没有新车厢可压。如果目标依旧无法位于栈顶，就失败。这条策略不会错失其他可能，因为只要目标能从栈顶弹出，延迟弹出它并不会帮助获得它下面的元素。

对于 n 个互异车厢按固定顺序进栈，所有合法出栈排列的数量恰是 Catalan 数 <code>C_n=binom(2n,n)/(n+1)</code>。比如 n=3 时有 5 种合法排列；n=6 时有 132 种。计数公式的证明依赖合法进出栈括号序列的对应关系，本章先把具体模拟和不可行性理由学扎实，后面树形计数会再次遇到同一个数列。

## 03.7 双栈共享数组 {#v4-sharedstack}

<p class="section-epigraph">为什么两个栈能够共享一整块数组</p>
最后回到实现问题，看看“栈只能在一端操作”还能带来什么设计。若需要两个容量可变但总占用不超过 m 的栈，分别给它们固定分配 m/2 格并不灵活：一个已经满了，另一个可能还剩很多空位。能不能让它们使用同一数组而互不干扰？

让栈 A 从数组左端向右增长，让栈 B 从数组右端向左增长，就能让两边共享尚未占用的中间区间。这里仍约定两个 top 都指向各自的**实际栈顶元素**：初始 <code>topA=-1</code>，因为左栈空；<code>topB=m</code>，因为右栈空。A 入栈先 ++topA，B 入栈先 --topB。

假设 m=8，topA=2、topB=6。这意味着 A 占据下标 0、1、2；B 占据下标 6、7；中间仍空着 3、4、5，合计三格。如果 A 连续入三项，它将占据 3、4、5，此时 topA=5、topB=6，中间已经没有空位；再向任意一边压栈会发生覆盖。因此满条件是 <code>topA+1==topB</code>。

请自己比较这种实现与循环队列：它们都利用数组下标管理有效区间，但共享栈的增长方向相向，循环队列的下标是在同一方向取模回绕。结构的逻辑操作不同，数组下标规则也必然不同。

## 03.8 本章综合练习 {#v4-stack-exercises}

<p class="section-epigraph">章节练习：完整题意、提示与过程</p>
下面的题目默认你已经读完本章。每道题先给完整输入、约定及任务，再提供可展开的思路和答案。建议先自己画出“输入位置／栈／输出”三列，至少做完一轮模拟再查看解答。



#### 练习 1｜栈的基本操作与下标（基础，6 分）

**题目。** 有一个容量为 4 的顺序栈，<code>top</code> 表示最后一个有效元素下标，初始 top=−1。依次执行 push(3)、push(8)、pop、push(5)、push(9)、top、pop。请写出每一步结束后的 top 值、栈内元素（从栈底到栈顶），并指出两次 pop 的返回值与 top 的返回值。假设所有操作都合法。

<details class="question"><summary>查看思路与解答</summary>

**思路。** 先按 top=−1 判空；push 先增加 top，再写值；pop 先读值，再减少 top。不要把已弹位置里可能残留的整数当作栈元素。

**解答。** 七步操作后的 top 依次为 0、1、0、1、2、2、1；有效栈依次为 [3]、[3,8]、[3]、[3,5]、[3,5,9]、[3,5,9]、[3,5]。两次 pop 返回 8、9；top 返回 9，且不改变栈。可以用每步“有效项个数=top+1”复核。

**易错点。** 若把 top 误解释为下一空位，会出现全部结果差一的错误；若 top 查询后误减一，最后栈状态也会错。

</details>



#### 练习 2｜括号序列判断（基础到作业同级，8 分）

**题目。** 给定两个输入字符串 <code>{[(a+b)*c]}</code> 和 <code>([)]</code>。只把圆括号、方括号和花括号视为需要配对的字符，变量和运算符直接跳过。判断每个字符串是否合法；对于不合法的串，指出**首次可以确定失败的位置**。给出所需栈操作的时间复杂度。

<details class="question"><summary>查看思路与解答</summary>

**思路。** 从左到右处理，每次只对括号操作。右括号必须匹配当前栈顶，而不能寻找栈内任意位置的同类左括号。

**解答。** 第一串依次压入 {、[、(，遇 ) 弹 (、遇 ] 弹 [、遇 } 弹 {，最终空栈，因此合法。第二串先压入 (、[，第三个字符是 )，但栈顶左括号是 [，类型不匹配，因此在下标 2（0-based）就可以确定失败，无需继续扫描。输入长度为 n 时每个括号最多入栈、出栈各一次，时间 O(n)，最坏栈空间 O(n)。

**易错点。** 数量相等与类型匹配是两个不同条件；一个右括号不能越过栈顶去寻找更早出现的对应左括号。

</details>



#### 练习 3｜中缀转后缀（作业同级，10 分）

**题目。** 所有变量 A、B、C、D、E 都是单字符操作数；<code>+,-</code> 同级、<code>*,/</code> 同级且优先于加减；四种运算均左结合。将 <code>(A+B)*C-D/E</code> 转换为后缀表达式。必须说明遇右括号时如何处理运算符栈，最后写出完整后缀序列。

<details class="question"><summary>查看思路与解答</summary>

**思路。** 操作数直接输出，运算符在确定可以先执行时才输出。遇右括号时，把直到配对左括号以前的全部运算符弹出；左右括号均不进入输出区。

**解答。** 读取 ( 时压栈；A 输出；+ 压栈；B 输出；遇 ) 弹出 +，得到 A B +，同时丢弃左括号。读取 * 时压栈，C 输出；遇 - 时先弹 *，输出 A B + C *，再压入 -；D 输出；读取 / 时由于 / 优先级更高，压在 - 上方；E 输出；输入结束依次弹 /、-。最终为 <code>A B + C * D E / -</code>。

**易错点。** 在右括号处忘记弹出 +，或者把括号本身输出，会使后缀表达式丧失原有分组含义。

</details>



#### 练习 4｜带一元运算的逻辑表达式（提高，10 分）

**题目。** 设 <code>!</code> 为一元逻辑非，优先级最高；<code>&&</code> 次之；<code>||</code> 最低。括号优先，二元运算符均左结合。将 <code>!(A&&B)||C>D</code> 转为后缀表达式，其中关系运算 <code>></code> 的优先级高于 <code>&&</code>、低于 <code>!</code>，且只作用于 C 与 D。写出结果，并解释为何 <code>!</code> 的后缀求值不能弹出两个操作数。

<details class="question"><summary>查看思路与解答</summary>

**思路。** 先完成括号中的 A&&B，再对整个括号结果执行 !；另一侧先完成 C>D，最后执行 ||。

**解答。** A&&B 对应 <code>A B &&</code>；对它取逻辑非得到 <code>A B && !</code>；C>D 对应 <code>C D ></code>。最终是 <code>A B && ! C D > ||</code>。一元 ! 只针对一个布尔值取反，后缀计算栈中弹出一个操作数即可。若错误地弹两个，程序会把更早的计算结果错误消耗掉。

**易错点。** 不给出运算符优先级与元数就直接转换，可能产生多个不同解释；这道题已明确约定，不能自行改变。

</details>



#### 练习 5｜列车出栈序列（作业同级，10 分）

**题目。** 编号 1、2、3、4、5、6 的车厢只能按升序逐个进入一条栈式旁线。任一时刻可以把下一节车厢入栈，或把当前栈顶出栈。判断目标出站顺序 <code>3,2,5,6,4,1</code> 与 <code>3,1,2,4,5,6</code> 是否可行。对可行者写出每个 I/O 事件；对不可行者指出首次出现的无法消除的阻碍。

<details class="question"><summary>查看思路与解答</summary>

**思路。** 为实现目标第一个 3，都必须先入栈 1、2、3。此后尝试让栈顶与下一目标一致；若目标已经被压在栈内深处，就不能越过上方元素直接取它。

**解答。** 第一种可行，事件为 <code>I1 I2 I3 O3 O2 I4 I5 O5 I6 O6 O4 O1</code>。此时出站依次为 3、2、5、6、4、1，且所有 O 都从当前栈顶发生。第二种不可行：I1 I2 I3 O3 后旁线为 [1,2]，下一目标要出 1，但 2 压在上方；即使继续入栈也只能让更多车厢压在 2 上面，所以无法让 1 先出。

**易错点。** 任意选择未来编号进栈会违背固定入栈顺序；只给“可／不可”而不追踪栈顶，无法说明判断的可靠性。

</details>



#### 练习 6｜双栈共享数组（作业同级，8 分）

**题目。** 有一个下标为 0–9 的数组供两个栈共用。左栈 A 从左向右增长，右栈 B 从右向左增长，两个 top 均指向当前有效栈顶；空栈时 topA=−1、topB=10。若现在 topA=3、topB=7，请计算两个栈分别占据哪些下标、总共还可以再入栈多少项，并写出判满条件。如果下一步向 A 入栈一次、向 B 入栈两次，又是什么状态？

<details class="question"><summary>查看思路与解答</summary>

**思路。** 有效空闲区间严格位于 topA 与 topB 之间。边界上的 topA 和 topB 均是已经占用的槽位。

**解答。** 左栈占 0–3，右栈占 7–9，空闲为 4、5、6，共三格。满条件 <code>topA+1==topB</code>。A 入栈后 topA=4，B 两次入栈后 topB=5，此时没有空格，刚好满。整个过程不应覆盖任一已有栈元素。

**易错点。** 把 topB=7 当成下一空位置，会把空位数错误地算成四格。

</details>

**学完本章的最后检验。** 合上正文后，尝试解释：为什么括号匹配需要“最近未关闭”的信息；为什么中缀转后缀中某个运算符必须等另一个运算完成才输出；为什么列车目标顺序会出现“被栈顶挡住”的必然失败。三道问题共同说明栈如何保存和解决尚未完成的工作。弄懂这个联系，下一章的递归调用栈也就有了直观起点。
