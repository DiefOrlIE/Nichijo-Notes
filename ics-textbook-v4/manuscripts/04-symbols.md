# 4.1 编译、目标文件与符号解析——为每个引用找到定义

本篇按教材第五章5.1至5.3.2的顺序学习。只要求会C中的变量、数组和简单函数；编译阶段、目标文件、节、段、外部名字都在这里逐项建立。示例使用Linux常见C工具链，目录中保留课程第四章的对应关系。

## 编译和汇编——把一份C源码逐步变成机器代码

教材对照：§5.1.1，纸书第184页；附件PDF第975–976页。课程第四章PPT第4–9页。要求：需掌握。

假设`main.c`想打印一个由`sum.c`计算出的和。`main.c`知道函数`sum`接收两个`int`并返回`int`，却不知道`sum`最终会被放在哪个地址。`sum.c`则负责定义这个函数。分开编译可以让两个人独立修改各自文件，但最终机器指令调用`sum`时仍须找到真正入口。

先写一个完整的小程序。`main.c`内容如下：

```c
#include <stdio.h>
int sum(int a, int b);
int main(void) {
    printf("%d\n", sum(3, 5));
    return 0;
}
```

`sum.c`内容如下：

```c
int sum(int a, int b) {
    return a + b;
}
```

这些命令在装有C编译工具链的Linux终端执行；先用文本编辑器把两个代码块分别保存为`main.c`与`sum.c`，并把终端当前目录切到这两个文件所在目录。`cc`是编译驱动程序，-o后面给输出文件名，.o是本例目标文件名。`./demo`表示运行当前目录中的demo。

先分别执行`cc -c main.c -o main.o`和`cc -c sum.c -o sum.o`。-c表示生成目标文件后停止。`main.o`已有`main`的机器代码，但对`sum`的引用还没有找到外部定义；`sum.o`已有`sum`的定义。再执行`cc main.o sum.o -o demo`，链接器把引用与定义关联，安排代码和数据的位置，修补受位置影响的字段，生成demo。运行`./demo`输出8。


把生成过程再展开一次，才能分清报错发生在哪一步。`#include`在预处理阶段把声明等文本放入当前翻译单元；编译阶段分析C语义并产生汇编表示；汇编阶段编码为机器指令，同时留下需要以后确定的地址记录；链接阶段才组合不同目标模块。上面的`cc -c`让驱动程序执行前三步后停止。它没有完成最后的链接。

如果希望看见中间产物，可在同一目录继续执行：

```sh
cc -E main.c -o main.i
cc -S main.i -o main.s
cc -c main.s -o main.o
```

`-E`停在预处理后，`main.i`仍是可读文本；`-S`停在编译后，`main.s`是汇编文本；`-c`得到的`main.o`是二进制目标文件。`-o`只指定输出文件名，它不决定停止阶段。三个产物存放的对象不同，所以不能靠把`.o`改名为`.s`让它变成汇编文本。

声明`int sum(int,int);`向编译器说明调用接口，使它有依据检查参数并产生调用代码。声明本身没有给出加法实现。`main.o`因此可以在尚未读到`sum.c`的情况下生成；它把未完成的连接工作交给后续阶段。这正是单独编译可行的前提。

### 即时练习：判断失败阶段（教材题2(1)同级训练）

题目：漏写一个分号、把`sum.o`遗漏在最终命令之外、运行时缺少共享库，分别应该先检查哪一阶段？

提示：按“C文本是否有效—目标模块是否齐全—运行依赖是否可找到”依次判断。

解答：分号错误先在编译阶段修复；遗漏`sum.o`使链接阶段找不到外部定义；缺少共享库属于运行时加载依赖问题。重新检查这三种错误各自还没有得到哪个产物，便能避免用重新声明函数去修复缺少机器实现的问题。

## 可执行文件的生成——把分开的引用与实现连在一起

教材对照：§5.1.2，纸书第185–186页；附件PDF第976–978页。课程第四章PPT第9–14页。要求：需掌握。

链接的两项主要任务由此产生。符号解析回答“这个名字引用哪一个定义”；重定位回答“定义落在哪个位置，引用处应填什么数”。两者有依赖：先知道`sum`指向哪个函数，再按该函数的位置计算调用字段。

若只执行`cc main.o -o demo`，通常会报告`undefined reference`，即未定义引用；编译`main.c`成功只说明这一模块通过相应检查，没有保证最终存在`sum`实现。若只改`sum.c`，通常只需重编`sum.o`再链接，`main.o`可复用。模块化和增量构建正是链接的重要用途。

### 教材练习：第五章题2(1)、2(2)、2(4)（题意转述）

请描述多个C模块如何生成可执行文件、链接带来什么便利，以及静态链接主要完成什么工作。先用上面两个文件说明，再给一般结论。

提示：区分“分别生成.o”和“把.o连成可执行文件”，不要把#include当成链接。

解答：每份源文件经预处理、编译、汇编生成可重定位文件，再把相关目标文件和所需库模块交给链接器。链接器进行符号解析与重定位。好处包括模块划分、代码复用、单独编译和只重建修改部分。头文件提供声明等文本，不会自动给`main.o`补上另一个目标文件中的机器代码。

还可以用反汇编验证连接到底改变了什么。`objdump -d main.o`中的地址通常按当前输入节显示，函数起点可能为0；它没有宣告该函数最终要占据虚拟地址0。`objdump -d demo`显示的是链接结果的地址布局。编译器或链接器还可能加入启动代码、对齐字节和运行库信息，因此两个目标文件的长度相加通常不能直接得到可执行文件的长度。

运行`./demo`最终取得8，只验证了这次生成的程序。为了检查模块化是否真的生效，可以只把`sum.c`中的`a+b`改成`a+b+1`，重编`sum.o`后再链接，不重新生成`main.o`；输出随实现变成9。做完请把实现改回原来的加法。调用接口未变时，未修改模块的目标文件可以复用；若接口发生变化，调用者也可能需要重编。

## ELF目标文件格式——让后续工具读懂目标文件

教材对照：§5.2.1，纸书第188页；附件PDF第987页。课程第四章PPT第15–18页。要求：需掌握。

刚才的`.o`已经包含机器指令，却还需要告诉链接器哪些字节属于代码、哪个名字尚未定义、哪些字段等待修补。如果把这些信息随意混在一起，下一个工具就无法可靠地读取。因此目标文件要采用约定好的二进制格式。

ELF是Executable and Linkable Format，可执行与可链接格式。Linux中常见的可重定位文件、可执行文件、共享目标均可采用ELF。文件头说明位宽、字节序、目标机器和文件类型，并给出后续表的位置。看到ELF不能立即推出它可以独立启动：文件类型和所含装入信息还要继续检查。

链接器关心“把哪些输入材料合成输出”，按节组织内容；加载器关心“把哪些文件范围映射到哪里、允许怎样访问”，按段组织运行布局。两张视图服务不同任务。可以先把它们想成同一份档案的两张索引：节头表按内容分类，程序头表按装入需求分类。它们描述的是同一文件里的字节，不能因此认为每个节必须单独对应一个段。

用`readelf -h main.o`和`readelf -h demo`比较文件类型，再用`readelf -S main.o`查看节，最后用`readelf -l demo`查看装入段。这里`readelf`只读取和解释文件，不会执行它。输出顺序和地址随工具链改变，先认字段的职责，再对照数值。

## 可重定位文件格式——找出代码、数据与尚待连接的信息

教材对照：§5.2.2，纸书第189–191页；附件PDF第988–993页。课程第四章PPT第18–26页。要求：需掌握。

现在集中看一个尚未链接的模块。`.text`通常保存函数机器代码，`.rodata`通常保存只读常量，`.data`保存有初始内容的可写静态对象，`.bss`为零初始化或未显式初始化的静态存储对象保留空间。普通自动局部变量随调用建立，它的值通常位于栈或寄存器，不能因为源代码里有一个名字就给它分配一个静态数据节。

例如把`int ready=7;`、`int idle;`和`static int hidden=2;`写在文件作用域。常见工具链会把7和2的内容字节放在`.data`，把`idle`的零初始化需求放在`.bss`。字符串常量可能进入`.rodata`，函数指令进入`.text`。编译优化和符号生成选项会影响具体结果，观察时要写明使用的命令。

文件还需要保存连接所需的说明书。`.symtab`记录符号身份与位置，字符串表保存名字，`.rel.text`等重定位节指出要修改的字段；某些平台使用把加数单独记录的`.rela.*`形式。节头表给出节名、类型、文件偏移、大小、对齐等信息。`.bss`常用`NOBITS`类型：表里记录需要多大空间，文件没有为每个初始零另存一个字节。

这里出现了三个不能混算的量。文件偏移指出从文件开头数到哪里；节内偏移指出某符号距该输入节起点多远；运行时虚拟地址要等布局确定。假设`sum`在输入`.text`偏移0x10，最终该输入节被放到0x400600，它的虚拟地址才是0x400610；文件中这些指令存放在哪里，还要根据输出文件布局查找。

提示：先判断“本模块提供定义”“引用别处定义”“随调用存在”，再判断存储位置。

解答：被实际引用的`other`需要一个未定义外部符号记录，其存储由定义模块提供；`ready`在本模块提供静态对象定义，常见情况下属于`.data`，可重定位阶段记录节内值；`temp`通常由栈偏移或寄存器描述，不参与这类普通跨模块符号解析。调试信息中可能记录`temp`，这与普通链接符号是两种用途。

## 可执行文件格式——从文件范围建立可装入的布局

教材对照：§5.2.3，纸书第192–193页；附件PDF第994–996页。课程第四章PPT第27–32页。要求：需掌握。

将各模块连接后，可执行文件仍然可以保留`.text`、`.data`等节。但启动程序时，加载器首先需要的是装入段：从文件哪一处开始，取多少字节，映射到哪个虚拟地址，剩下多少字节置零，设置哪些权限。这些要求由程序头表描述。

对一个`PT_LOAD`表项，`p_offset`是源文件偏移，`p_vaddr`是目标虚拟地址，`p_filesz`是来自文件的字节数，`p_memsz`是运行时区域大小，权限标志说明可读、可写、可执行等要求。文件头中的入口地址指出建立初始环境后从哪里开始执行。它通常指向启动代码，不能直接当成C函数`main`的地址。

先用一个没有分页细节的模型算一轮。若某段从文件偏移0x400取0x80字节，映射到虚拟地址0x8048400，文件偏移0x430对应的虚拟地址就是0x8048400加上相对位移0x30，结果0x8048430。位移来自0x430−0x400，不能把文件偏移直接当成目标地址。只有落在该段文件内容范围内，才使用这次对应关系。

若同一表项的内存长度是0xA0，末尾多出的0x20字节要零初始化。于是文件区间是0x400至0x47F，而映像区间是0x8048400至0x804849F。一个是文件中的位置，一个是进程里的位置，长度和端点都应该分别核对。

### 即时练习：在表项里找位置（教材题2(8)同级训练）

题目：上述文件偏移0x470应映射到哪里？文件偏移0x490能否直接套用同一映射公式？

提示：先检查文件内容范围，再计算相对段起点的位移。

解答：0x470在有效文件区间内，位移0x70，对应0x8048470。0x490超过该表项的`p_filesz`范围，不能据此认为存在来自该位置的文件字节；映像尾部的零填充也不要求从文件0x490读取。范围检查比先代公式更重要。

## 可执行文件的存储器映像——分清磁盘中的字节和进程中的地址

教材对照：§5.2.4，纸书第194页；附件PDF第997–998页。课程第四章PPT第12、30、33–34、76–78页。要求：需掌握。

程序现在获得了一套运行地址。虚拟存储器映像描述代码、只读数据、可写数据、零初始化区域等在进程虚拟地址空间中的安排；它还会与运行时堆、共享库映射、用户栈等区域共同构成运行环境。虚拟地址首先属于当前进程的地址空间，不直接等同于磁盘偏移或物理内存位置。

教材用典型老32位Linux布局展示只读代码段和可读写数据段，代码映像常以0x8048000一带为例。做题时应遵循题目指定的布局；实际系统可采用多个具有不同权限的装入段，并通过位置无关可执行文件和地址随机化改变基址。不能把教材图中的一个具体起点背成所有程序共有的地址。

一个装入段可以覆盖多个相邻的节。例如`.text`与某些只读内容适合进入可读取或可执行的映射，`.data`和`.bss`需要可写映射。代码复用和权限保护都以这样的映射为基础；可写区域不会因为与共享代码同属一个库就自动成为所有进程共享的一份数据。

再看教材题8的原始长度数据：文件从0x448起提供0xE8字节，虚拟空间从0x8049448起需要0x104字节。先算0x104−0xE8=0x1C，再换算为28字节。因此来自文件的部分延伸到0x804952F，额外零填充从0x8049530到0x804954B。文件无需为这28个零逐字节占位；具体归属仍要结合节与段布局判断。

### 教材第五章题8（原题数据转述）

题目：解释上面28字节的差，并判断它是否意味着文件缺失了数据。

提示：把“文件提供的内容长度”和“运行时必须存在的区域长度”分开。

解答：差值是零初始化等运行时需求，通常包括`.bss`内容，长度为0x1C。它由加载语义保证，不能仅凭两种长度不等判定文件损坏。用0xE8+0x1C=0x104回算长度，再检查两段虚拟区间首尾连续，就能独立核对。

## 符号和符号表——以当前模块为参照辨认每一个名字

教材对照：§5.3.1，纸书第195–198页；附件PDF第1047–1049页。课程第四章PPT第36–39页。要求：需掌握。

考虑模块`a.c`：

```c
int shared = 7;
static int local = 2;
extern int other;
int calc(void) {
    static int times;
    int temp = shared + other;
    ++times;
    return temp + local + times;
}
```

从链接器视角逐项读。`shared`具有外部链接，`a.o`提供其定义；`local`具有内部链接，别的模块不能用同名外部引用直接找到它；`other`只有外部声明，本模块使用它，因此需要另一模块提供定义；`calc`提供函数定义；`times`具有静态存储期，通常也需要一个内部符号定位；`temp`是本次调用的自动局部对象，通常由栈偏移或寄存器描述，不作为跨模块解析的普通链接符号。调试信息可以包含局部变量名，不能由此说它必定属于普通链接符号集合。

符号表的记录通常给出名字、绑定属性、所属节和节内值等。若在`a.o`中查看，`shared`的“位置”可能只是相对于.data的偏移；链接合并后才得到输出布局中的地址。一个符号是“本模块定义”还是“本模块引用”，要以当前目标模块为参照。同一名字在`a.o`里未定义，在`b.o`里可以有定义。

### 对应教材第五章题3、题4的同类训练（本题为改编）

按上面的`a.c`，在不假设优化消除对象的条件下，分别判断`shared`、`local`、`other`、`calc`、`times`、`temp`是否属于需要链接器处理的符号，以及定义位置。

提示：先判断对象是否有静态存储期或是否为函数，再区分本地定义与外部引用。变量的“局部作用域”并不必然意味着“在栈上”。

解答：`shared`在`a.o`定义，通常.data；`local`在`a.o`内部定义，通常.data；`other`在`a.o`为未定义外部引用，节归属由定义模块决定；`calc`在`a.o`定义于.text；`times`在`a.o`内部定义，零初始化通常.bss，编译器可能给它带后缀的符号名；`temp`为自动局部对象，不参与这类跨模块符号解析。`times`虽然只在函数内可见，却需要跨多次调用保留状态。

## 符号解析——为引用选择合适且可见的定义

教材对照：§5.3.2，纸书第199–201页；附件PDF第1050–1052页。课程第四章PPT第40–49页。要求：需掌握。

先不把整个系统库一起搬上纸，只追踪本例由我们编写的两个名字。读`main.o`时，`main`属于已经找到的定义，`sum`属于已经被引用却尚未找到的名字。再读`sum.o`，遇到`sum`的定义，就把`main.o`中记录的`sum`引用指向它。`printf`也需要定义，但由后续系统库提供；编译驱动通常还加入启动文件等输入，这正是推荐用`cc`完成普通C程序链接而不随意直接调用`ld`的原因。

对一个引用，链接器查符号绑定与可见性以决定可选择范围。`main.o`中的外部`sum`可以由另一个模块提供；若`sum.c`把定义写成`static`，该名字只在自己的模块内部可用，`main`的外部引用仍未解决。这样就能解释“文件里明明有同名函数为什么仍报未定义”：拼写相同只是候选条件，还要检查是否对外提供。

现在把`sum`从源代码中的名字连接到目标文件中的记录。`sum.o`的符号记录会表明它属于.text，其值在可重定位阶段通常是节内偏移。若`sum`在该节偏移0，最终该输入代码被安排到1020H，函数地址才成为1020H。符号解析确定选择哪个`sum`，布局与重定位才使用这个位置。把这三个时刻分开后，读符号表中的0便不会误认为函数最终地址一定为零。

先区分语言声明、目标文件符号属性与旧教材的`COMMON`规则。文件级`extern int x;`是声明，若未引用它，目标文件甚至不必保留相应未定义符号；文件级`int x=1;`提供定义；文件级`static int x;`提供模块内部对象，不与其他模块的同名内部对象冲突。

在课件采用的常见传统模型中，普通已初始化全局变量和函数属于强定义，文件级暂定定义`int x;`可被编译成`COMMON`。一个强定义与`COMMON`相遇时选强定义；多个`COMMON`可按规则合并，大小/对齐通常取足够大的要求；两个同名强定义通常导致重复定义错误。显式`weak`属性产生的弱符号是另一种目标文件绑定，不能把所有`COMMON`与ELF弱绑定完全画等号。

现代GCC默认`-fno-common`，`int x;`通常直接成为.bss中的定义。于是两个文件都写`int x;`可能在链接时报重复定义，旧课件在`-fcommon`模型下却可能链接通过。做教材题先写采用哪种模型；做工程代码，应在头文件声明`extern int x;`，在一个源文件中提供唯一定义。

危险不止重复名字。若一个文件定义`int x`，另一文件错误声明`extern double x`，普通链接器通常不会按C语言的完整类型检查修复这种不匹配。后者可能以八字节访问一个四字节对象，形成未定义行为并破坏相邻数据。应共享同一头文件，避免各模块分别猜接口。

先把类型错配的后果落到一个明确的机器模型。假设某题指定小端布局，四字节`x`位于0x1000、四字节`z`紧接在0x1004，初值分别是257和2。初始八字节为`01 01 00 00 02 00 00 00`。若另一模块错误地按八字节对象访问`x`，一次八字节写入会覆盖整个0x1000–0x1007，连`z`所在的后四字节也受到影响。按机器字节能分析这份指定布局，但这些不兼容声明已违反C要求，实际C程序没有由此得到可移植的输出保证。修正应从各模块共享正确声明开始。

为免把旧规则背成“所有同名变量都会合并”，再逐步处理两个模块。甲有`int` `x`=3，乙有`extern` `int` `x`并读取：乙没有提供第二个对象，外部引用指向甲。若乙改为`int` `x`=9，则两个强定义争用同一外部名字，通常拒绝链接。若乙改为`static` `int` `x`=9，则两个对象各有身份，不再争用同一外部定义，乙读自己的9。最后若两个文件均写`int` `x`，必须先说明`-fcommon`还是`-fno-common`；同一段C文本在两种目标符号生成规则下可能得到不同链接诊断。

### 教材第五章题6的同类训练（改编）

甲模块定义`int x=3;`，乙模块含`extern int x;`并读取`x`；这次引用关联到哪里？再将乙改成`static int x=9;`，读取结果如何变化？

提示：先沿本节正文的完整示范建立初始状态，逐步应用同一规则；完成后用逆向计算或边界输入复查。

解答：第一种乙的外部引用关联甲的定义，读3。第二种乙定义自己的内部对象，乙对`x`的引用关联乙自身，读9，甲的外部`x`仍独立存在。不能因为拼写相同就把两个内部与外部对象强行合并。


### 练习：从报错反推阶段

题目：甲文件调用`sum`，声明正确，单独生成.o成功；最终链接却报`sum`未定义。给出两种不同成因，以及怎样用目标文件检查它们。

提示：检查定义文件有没有加入输入，并检查定义是不是对外可见。

解答：一是`sum.o`未参与链接，二是`sum`被定义为`static`而没有提供外部定义。可用nm或`readelf`查看输入符号，找外部`sum`的未定义记录与可用定义；仅在源文件里搜索同名字符串不足。补入正确目标文件或修正接口后重新链接，才构成实际核对。不能靠在头文件重复声明制造机器实现。

本节解决了名字如何找到定义。若定义藏在一个含许多成员的归档里，链接器还要判断取出谁、何时取出，这就是下一节的需求。

### 教材题5、题7的阅读边界

题5与题7把类型、字节布局和符号解析放在一起。先用链接规则找出每个引用最终落在哪个对象，再按实际访问宽度追踪字节。若一个模块将同名对象声明为不兼容类型，链接成功不代表C语义有效，也不能把某次机器上观察到的输出说成可移植保证。题7涉及把函数入口的机器字节当数据观察，应按题给平台与反汇编解释；不要把函数名相同理解成类型检查已经通过。
