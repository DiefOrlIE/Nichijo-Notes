# 4.1 目标文件与符号解析——让分开的模块找到彼此

## 一份源文件为什么不能确定所有地址

假设main.c想打印一个由sum.c计算出的和。main.c知道函数sum接收两个int并返回int，却不知道sum最终会被放在哪个地址。sum.c则负责定义这个函数。分开编译可以让两个人独立修改各自文件，但最终机器指令调用sum时仍须找到真正入口。

先写一个完整的小程序。main.c内容如下：

```c
#include <stdio.h>
int sum(int a, int b);
int main(void) {
    printf("%d\n", sum(3, 5));
    return 0;
}
```

sum.c内容如下：

```c
int sum(int a, int b) {
    return a + b;
}
```

这些命令在装有C编译工具链的Linux终端执行；先用文本编辑器把两个代码块分别保存为main.c与sum.c，并把终端当前目录切到这两个文件所在目录。cc是编译驱动程序，-o后面给输出文件名，.o是本例目标文件名。`./demo`表示运行当前目录中的demo。

先分别执行`cc -c main.c -o main.o`和`cc -c sum.c -o sum.o`。-c表示生成目标文件后停止。main.o已有main的机器代码，但对sum的引用还没有找到外部定义；sum.o已有sum的定义。再执行`cc main.o sum.o -o demo`，链接器把引用与定义关联，安排代码和数据的位置，修补受位置影响的字段，生成demo。运行`./demo`输出8。

链接的两项主要任务由此产生。符号解析回答“这个名字引用哪一个定义”；重定位回答“定义落在哪个位置，引用处应填什么数”。两者有依赖：先知道sum指向哪个函数，再按该函数的位置计算调用字段。

若只执行`cc main.o -o demo`，通常会报告undefined reference，即未定义引用；编译main.c成功只说明这一模块通过相应检查，没有保证最终存在sum实现。若只改sum.c，通常只需重编sum.o再链接，main.o可复用。模块化和增量构建正是链接的重要用途。

## 在两个输入文件间实际走一次解析

先不把整个系统库一起搬上纸，只追踪本例由我们编写的两个名字。读main.o时，main属于已经找到的定义，sum属于已经被引用却尚未找到的名字。再读sum.o，遇到sum的定义，就把main.o中记录的sum引用指向它。printf也需要定义，但由后续系统库提供；编译驱动通常还加入启动文件等输入，这正是推荐用cc完成普通C程序链接而不随意直接调用ld的原因。

对一个引用，链接器查符号绑定与可见性以决定可选择范围。main.o中的外部sum可以由另一个模块提供；若sum.c把定义写成static，该名字只在自己的模块内部可用，main的外部引用仍未解决。这样就能解释“文件里明明有同名函数为什么仍报未定义”：拼写相同只是候选条件，还要检查是否对外提供。

现在把sum从源代码中的名字连接到目标文件中的记录。sum.o的符号记录会表明它属于.text，其值在可重定位阶段通常是节内偏移。若sum在该节偏移0，最终该输入代码被安排到1020H，函数地址才成为1020H。符号解析确定选择哪个sum，布局与重定位才使用这个位置。把这三个时刻分开后，读符号表中的0便不会误认为函数最终地址一定为零。

## ELF里同时存在两种组织视角

ELF是Executable and Linkable Format，可执行与可链接格式。Linux常见的.o、可执行文件和.so共享目标均可采用这一格式。它们都有文件头等结构，但承担的工作不同。

可重定位文件保存尚待组合的代码、数据、符号和重定位记录；可执行文件保存装入执行所需的布局；共享目标文件支持在加载或运行时参与动态链接。不能只凭扩展名判断所有属性，应读取文件头中的类型。

链接器需要把不同文件中的同类内容合并，因而按节section观察文件。`.text`通常放机器代码；`.rodata`放只读常量，例如某些字符串；`.data`放具有已初始化内容的可写静态存储对象；`.bss`为零初始化或未显式初始化的静态存储对象预留空间。`.bss`记录大小与布局，通常不在磁盘上为全部零内容逐字节占位。

加载器更关心“把哪段文件字节映射到哪里、给什么权限”，按段segment观察文件。程序头表描述可装入段的文件偏移、虚拟地址、文件大小、内存大小和访问权限。节头表描述各节的信息。一个段可包含多个节，因此不能把节与段当成一一对应关系。

例如代码节和某些只读数据可位于具有读取权限的装入区域，可写数据和零填充区域位于可写装入区域。老教材把典型布局概括为只读代码段与可读写数据段，现代链接器可进一步分成只读、可执行、可写等多个PT_LOAD段。处理具体题目时按给出的程序头表计算。

把这个组织方式用于具体对象：假设a.o有16字节代码和一个初始化为7的int，b.o有8字节代码和一个未显式初始化的int。简化布局可以把两份代码连成24字节的输出.text，把7的四个内容字节放入.data，并为零初始化对象在.bss保留4字节。真实链接还会加入对齐填充和其他输入，不能把这个24字节教学模型当作实际文件全部大小。代码、数据和元信息均有自己的位置，ELF文件头也占字节。

## 给每个符号一张身份卡

考虑模块a.c：

```c
int shared = 7;
static int local = 2;
extern int other;
int calc(void) {
    static int times;
    int temp = shared + other;
    ++times;
    return temp + local + times;
}
```

从链接器视角逐项读。shared具有外部链接，a.o提供其定义；local具有内部链接，别的模块不能用同名外部引用直接找到它；other只有外部声明，本模块使用它，因此需要另一模块提供定义；calc提供函数定义；times具有静态存储期，通常也需要一个内部符号定位；temp是本次调用的自动局部对象，通常由栈偏移或寄存器描述，不作为跨模块解析的普通链接符号。调试信息可以包含局部变量名，不能由此说它必定属于普通链接符号集合。

符号表的记录通常给出名字、绑定属性、所属节和节内值等。若在a.o中查看，shared的“位置”可能只是相对于.data的偏移；链接合并后才得到输出布局中的地址。一个符号是“本模块定义”还是“本模块引用”，要以当前目标模块为参照。同一名字在a.o里未定义，在b.o里可以有定义。

## 多个同名定义怎样处理

先区分语言声明、目标文件符号属性与旧教材的COMMON规则。文件级`extern int x;`是声明，若未引用它，目标文件甚至不必保留相应未定义符号；文件级`int x=1;`提供定义；文件级`static int x;`提供模块内部对象，不与其他模块的同名内部对象冲突。

在课件采用的常见传统模型中，普通已初始化全局变量和函数属于强定义，文件级暂定定义`int x;`可被编译成COMMON。一个强定义与COMMON相遇时选强定义；多个COMMON可按规则合并，大小/对齐通常取足够大的要求；两个同名强定义通常导致重复定义错误。显式weak属性产生的弱符号是另一种目标文件绑定，不能把所有COMMON与ELF弱绑定完全画等号。

现代GCC默认-fno-common，`int x;`通常直接成为.bss中的定义。于是两个文件都写`int x;`可能在链接时报重复定义，旧课件在-fcommon模型下却可能链接通过。做教材题先写采用哪种模型；做工程代码，应在头文件声明`extern int x;`，在一个源文件中提供唯一定义。

危险不止重复名字。若一个文件定义`int x`，另一文件错误声明`extern double x`，普通链接器通常不会按C语言的完整类型检查修复这种不匹配。后者可能以八字节访问一个四字节对象，形成未定义行为并破坏相邻数据。应共享同一头文件，避免各模块分别猜接口。

为免把旧规则背成“所有同名变量都会合并”，再逐步处理两个模块。甲有int x=3，乙有extern int x并读取：乙没有提供第二个对象，外部引用指向甲。若乙改为int x=9，则两个强定义争用同一外部名字，通常拒绝链接。若乙改为static int x=9，则两个对象各有身份，不再争用同一外部定义，乙读自己的9。最后若两个文件均写int x，必须先说明-fcommon还是-fno-common；同一段C文本在两种目标符号生成规则下可能得到不同链接诊断。
