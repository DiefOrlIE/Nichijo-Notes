# 4.4 动态链接与库打桩——把共享实现接入运行环境

按教材5.5再到5.6的顺序阅读。共享库、加载时链接、运行时接口和PIC分别解决不同问题；库打桩单独标为未覆盖的选读内容。

## 动态链接的特性——让多个程序复用同一份库实现

教材对照：§5.5.1，纸书第210页；附件PDF第1101页。课程第四章PPT第82–84页。要求：需掌握。

静态库按需抽取解决了“只使用部分函数”的问题，但多个程序仍可能各自带上同一段实现。共享库把可复用的代码放在独立目标里，使多个程序能够依赖同一份库文件；操作系统在条件允许时还可让它们映射复用只读代码页。可写库数据和进程特定表项通常仍有各自状态，因此共享代码不能推出所有全局变量也在进程之间共享。

这种连接可以在加载时完成，也可以由程序运行后主动请求。前者适合启动时已经确定的依赖，后者适合插件等按需功能。两者都需要解决名字、地址与接口一致性：找到一个同名函数还不够，参数和返回值约定也必须匹配。

共享库更新后，不必把实现重新复制进每个使用者的文件。但这项便利有条件：ABI需要兼容，所需库必须能够被找到，依赖版本必须匹配。位置无关代码解决的是地址安排，不能替代版本管理。接下来先做一次普通加载时链接，再看运行时主动加载，最后解释为什么代码能放到不同基址。

## 程序加载时的动态链接——在启动路径上找到并连接依赖

教材对照：§5.5.2，纸书第210–211页；附件PDF第1101–1103页。课程第四章PPT第83、85–86页。要求：掌握加载时链接的基本过程；85–86页为补充跳转页。

若每个可执行文件都复制一份同样的库函数代码，磁盘和内存可能重复存储。共享库把可复用机器代码放在独立目标中，可执行文件记录依赖与必要动态信息。加载时动态链接器寻找库、建立映射、解析所需符号并完成必要修补；也可以在程序运行后显式打开某个库。

可以直接复用本章5.1.1的`main.c`与`sum.c`做一次共享库构建。采用Linux常见GNU工具链，先执行下列命令；三个命令各占一行。

```sh
cc -fPIC -shared sum.c -o libsum.so
cc main.c -L. -lsum -Wl,-rpath,'$ORIGIN' -o demo-shared
./demo-shared
```

第一行把`sum`做成共享目标，`-fPIC`请求位置无关代码，`-shared`请求共享库输出。第二行`-L.`让链接时到当前目录找库，`-lsum`按命名约定查找`libsum.so`或对应库；`-Wl`把后续选项交给链接器。这里把运行搜索路径设为`$ORIGIN`，表示可执行文件所在目录，单引号使终端不把它提前当环境变量展开。第三行运行输出8。链接时找到库与运行时找到库是两次搜索，只写`-L.`并不能保证搬动文件后的运行搜索成功。

此时`demo-shared`含对`libsum.so`的依赖，没有把所需`sum`实现按普通静态库抽取方式复制为同一种布局。可用`readelf` -d查看动态依赖记录，运行时动态链接器依据加载与搜索规则完成连接。修改库接口或移走库可能使执行失败，因此代码复用还伴随版本和部署条件。位置无关代码解决地址安排问题，不自动保证接口版本兼容。

在这个构建例子里，`-L.`只参与链接时的库搜索。运行时的动态链接器依照另外的搜索规则找`libsum.so`；命令中的`rpath`把`$ORIGIN`保留给运行时解释。把整个示例目录一起移动，程序仍可从自身所在目录查找该库；只移动可执行文件却不带库，运行可能失败。

可执行文件通过`PT_INTERP`等信息指定动态链接器；其`DT_NEEDED`记录依赖的共享目标。加载时先建立必要映射，动态链接器处理依赖、符号与需要立即完成的重定位，再把控制交给启动路径。某些函数绑定可以延后到首次调用，但这并不意味着启动前什么连接工作都不做。

### 即时练习：两次找库

题目：链接命令使用`-L.`成功生成程序，随后运行却报告找不到`libsum.so`。为什么编译成功仍不能保证启动成功？

提示：分别指出链接器和运行时动态链接器搜索发生的时刻。

解答：构建时找到了库以记录依赖和校验相应连接信息；启动时仍要按运行时规则定位实际文件。应核对部署目录及运行搜索路径，不能把`-L.`当成运行环境的永久设置。用`readelf -d`检查依赖和路径信息，再对照实际文件位置，是可执行的诊断顺序。

## 程序运行时的动态链接——需要某项功能时再打开它

教材对照：§5.5.3，纸书第212页；附件PDF第1104–1105页。课程第四章PPT第87页。要求：需掌握。

有些程序启动时并不知道以后要启用哪一个插件。若把所有可能功能都设成固定启动依赖，用户即使不用该功能，也可能因为少装一个库而无法启动。运行时动态链接允许程序在需要时通过接口打开库、查询符号，再按正确接口调用。

`dlopen`返回库句柄，用来标识本次打开的目标；`dlsym`在相应查找范围内寻找一个名字；`dlerror`报告错误；`dlclose`释放这次打开的关联引用。句柄与函数地址承担不同任务：句柄用于后续查询，函数地址才供调用。关闭句柄后也不能继续假定先前取得的函数地址永久有效。

继续使用`libsum.so`。先把运行路径想成三道关：打开库，查到名字，按约定调用。打开失败就停止；打开成功但查找失败，也必须停止并释放句柄。只有两次检查都通过，才把查得的地址当成约定接口使用。

下面给出Linux/POSIX环境的完整驱动。`void *`保存通用对象地址，`NULL`表示这里没有有效句柄；`int (*function)(int, int)`声明一个函数指针，表示它指向“接收两个`int`、返回`int`”的函数，`function(3,5)`才是真正调用。`RTLD_NOW`要求打开时完成相应符号解析，`RTLD_LOCAL`限制新载入目标的符号对后续查找的公开范围。这里借`memcpy`复制`dlsym`返回的地址表示，并检查本机函数指针与对象指针的大小；这一写法限于所注明的平台约定，不能推广为所有C实现的保证。

```c
#include <stdio.h>
#include <stdlib.h>
#include <string.h>
#include <dlfcn.h>
int main(void) {
    void *handle = dlopen("./libsum.so", RTLD_NOW | RTLD_LOCAL);
    if (handle == NULL) {
        fprintf(stderr, "%s\n", dlerror());
        return EXIT_FAILURE;
    }
    dlerror();
    void *address = dlsym(handle, "sum");
    const char *error = dlerror();
    if (error != NULL) {
        fprintf(stderr, "%s\n", error);
        dlclose(handle);
        return EXIT_FAILURE;
    }
    int (*function)(int, int);
    _Static_assert(sizeof function == sizeof address, "pointer size mismatch");
    memcpy(&function, &address, sizeof function);
    printf("%d\n", function(3, 5));
    return dlclose(handle) == 0 ? EXIT_SUCCESS : EXIT_FAILURE;
}
```

代码中的`_Static_assert`在编译时检查大小条件，`memcpy`复制给定字节数；它们不检验函数的参数类型。`EXIT_FAILURE`与`EXIT_SUCCESS`分别给出失败、成功的退出状态，`fprintf(stderr,...)`把错误写到标准错误输出。

把它另存为`plugin.c`，先生成前节的`libsum.so`，再执行`cc -std=c11 plugin.c -ldl -o plugin`与`./plugin`，预期输出8。先调用一次`dlerror()`清除旧错误，再在`dlsym`后读取错误状态，能避免把历史错误当成本次查询失败。程序在查询失败时停止，不会继续调用无效地址；函数签名仍须由双方共同约定。

这与延迟绑定是两个维度：程序可以在运行时主动`dlopen`一个库，同时要求`RTLD_NOW`立即解析相应需求；普通启动依赖也可能对某些函数采用延迟绑定。不要把“运行中查库”和“第一次调用才填表”混成一个概念。

### 迁移练习：插件缺失时怎样安排路径

题目：可选导出功能依赖一个插件，而主程序的基础功能不依赖它。插件不存在时，怎样安排控制流才能保留基础功能？

提示：检查打开结果，并在得到可用函数地址之前阻止调用。

解答：基础路径正常启动；用户请求导出时才打开插件，失败则给出该功能不可用的结果，返回基础路径。打开成功后还要检查符号查询与接口版本。把错误检查放在调用之后，已经无法阻止无效调用。

## 位置无关代码——改变基址后仍保持正确访问

教材对照：§5.5.4，纸书第213–217页；附件PDF第1106–1112页。课程第四章PPT第88–94页。要求：需掌握。

现在考虑共享库被放到不同基址的情况。代码里的一个固定绝对地址若随基址改变，就可能需要修改每个使用者的代码页，妨碍共享。PIC是Position-Independent Code，即位置无关代码。它尽量把可共享的指令保持为同一组字节，将必须随运行地址变化的内容放入适合修补的数据位置。

先看模块内部的相对调用。源和目标一起平移时，两者之差保持不变。假设调用后继原为0x105、目标0x120，位移0x1B；整个模块平移0x1000后，后继0x1105、目标0x1120，相减仍是0x1B。这直接延续了5.4.2的重定位核对。

访问本模块可确定的局部数据也可借相对位置。IA-32教材用一小段`call`取得后继地址，再把栈上的返回地址送入寄存器，最后加上已知位移找到数据；x86-64常用RIP相对寻址。具体机器实现不同，但都是先取得运行时参照，再利用固定距离。对允许符号插入覆盖的全局定义，还需要遵循实际绑定规则，不能一律当成不可改变的模块内部局部符号。

模块外变量不一定与本模块保持固定距离，因此引入GOT，Global Offset Table，全局偏移量表。代码先找到本模块附近的表项，再读出其中保存的外部变量实际地址。若`b`的地址为0x9000，GOT槽位位于0x6000，第一步读槽位得到0x9000，第二步才沿0x9000访问`b`。0x6000、0x9000和`b`当前保存的数是三个不同量，不能混写。

外部函数调用可通过PLT，Procedure Linkage Table，过程链接表。调用者跳到本模块的稳定入口，再经表项到达实际函数。典型延迟绑定第一次经过解析路径，动态链接器确定地址、更新表项并转入函数；下一次仍可调用同一入口，但沿更新后的地址直接跳转。立即绑定可以提前填表，是否延迟必须看实际选项与状态。

用两个表状态算完整路径：调用者的目标入口固定为0x5000，GOT槽位位于0x6000，最终函数地址为0x9000。初始槽位指向启动解析的路径；第一次调用进入0x5000后沿这条路径找到定义，把0x9000写进0x6000，再进入函数。第二次仍先到0x5000，读取槽位已得到0x9000，省去重复符号查找。函数正常返回时仍回到调用者保存的后继位置。

这里固定的调用入口解释了为什么调用者指令可以不因第一次解析而改写。GOT属于可随进程安排的运行状态，更新它不要求把所有进程共享的只读代码变成各自改写的副本。PIC与PIE也要区分：PIC描述代码生成方式，PIE是可按相应方式构建的位置无关可执行文件。现代工具链的实际布局未必与教材老32位例子逐字相同。

### 教材题2(10)与PLT状态训练

题目：第一轮调用结束后，0x6000处保存什么？第二轮是否仍到0x5000？这能否推出另一进程的同一槽位也已被修改？

提示：分别记录入口地址、槽位地址、槽位内容，最后再考虑进程边界。

解答：槽位保存0x9000；第二轮仍可从0x5000进入并经槽位跳到0x9000。不能推出另一进程的可写状态也改变，它可有独立映射与绑定状态。核对第一次和第二次路径中唯一被省去的解析工作，就能解释延迟绑定的缓存作用。

## 编译时打桩——选读：在源码翻译前接入包装层

教材对照：§5.6.1，纸书第218页；附件PDF第1161页。PPT未涉及。要求：无需掌握（选读）。

本节及5.6.2、5.6.3未在上传的课程第四章与第五章PPT中出现，按当前范围无需掌握。以下保留翻书时能辨认概念的选读说明，不把它作为后续必需先修。

库打桩是在目标调用外加一层封装，以记录、统计或替换行为。编译时打桩在源代码进入后续翻译前改变调用：例如通过宏把`malloc`调用重命名成包装函数。包装函数记录申请大小，再按正确方式调用原分配函数。

它需要重新编译相应调用者，并受头文件、宏作用域等条件约束。若包装函数里的真实调用又被同一宏替换，便会重新进入自己，造成递归。阅读此类程序时先圈出哪些源码受到宏替换，再追踪包装函数如何到达原实现。

## 链接时打桩——选读：在链接阶段改变引用的去向

教材对照：§5.6.2，纸书第219页；附件PDF第1162–1163页。PPT未涉及。要求：无需掌握（选读）。

链接时打桩利用链接器的符号重定向规则，在生成结果时把某些引用改接到包装实现。GNU链接器的`--wrap`机制是一个具体例子：对某名字的未解决引用可以转向相应`__wrap_`实现，包装层再使用约定的`__real_`名字访问原目标。

它影响的是符合规则的链接引用，不能保证捕获被内联的调用，或已经在其他位置完成内部绑定的路径。与编译时打桩相比，改变发生在后续连接阶段；核对重点从宏展开转成“这个引用最终关联哪个定义”。本节只需作为教材选读定位。

## 运行时打桩——选读：利用运行时的符号解析环境

教材对照：§5.6.3，纸书第220–221页；附件PDF第1163–1164页。PPT未涉及。要求：无需掌握（选读）。

运行时打桩在动态符号解析环境允许的条件下，使某个包装实现先被选中，再由包装层查找和调用实际实现。常见示例涉及动态加载器的查找顺序，但效果受安全执行模式、符号可见性、绑定时机和调用是否已被优化等条件限制。

这三种方法可按介入时机区分：预处理或编译时改写调用、链接时改变引用关联、运行时影响动态解析。它们共同要求接口一致，并需要防止包装层再次调用自身。无论在哪个阶段，找错签名或绕过错误检查都可能破坏程序；仅掌握普通静态链接并不自动保证能安全实现所有包装。
